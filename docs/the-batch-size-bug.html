The Batch Size Bug
Forget · benchmarking notes

The batch size bug my benchmarks found

A write-up of what happened when I benchmarked a Dapper extension honestly against hand-written Dapper and EF Core — including a real bug in already-shipped code that the benchmarks caught before a user would have, and a second chase, one release later, for a gap the first round of fixes didn't quite close.

Forget is a thin, provider-aware layer over Dapper for MySQL, Oracle, PostgreSQL and SQL Server: type-safe CRUD, filtering, sorting and paging, each translated into the SQL that engine actually wants. This isn't a "here's my library" post. It's what happened when I sat down to benchmark it properly.

The rule: publish the numbers even where they don't flatter you

The benchmark suite lives in the repository, runs with BenchmarkDotNet against real PostgreSQL containers, and its results are in the README as they came out, not cherry-picked. If Forget loses to something, that's in there too. That rule is what actually produced this post: it's easy to stop measuring once the numbers look good enough to publish. It's harder, and more useful, to keep asking "why does this specific number move the way it does," even after you've already got a number you're happy to show people.

Two of those "why" questions turned into real findings. The third turned into a bug fix. A fourth, one release later, turned into a smaller gap than any of these — and into watching an obvious-looking fix make things worse before it made them better.

Reads bottleneck on round trips

GetByIdRange fetches many rows by id in one call. Forget batches the ids — 500 per round trip by default — partly to stay under some engines' parameter limits (SQL Server accepts at most ~2,100 per command) and partly to avoid handing the database one statement with thousands of parameters. Dapper's hand-written equivalent and EF Core's own query both send all the ids in a single = ANY(...) / IN (...), regardless of count.

That difference should show up as more ids costing Forget more round trips, and it does. What's less obvious is which way EF Core's own number moves as ids grow:

idsForget, default batch (500)EF Core
1001.05x Dapper1.30x Dapper
1,0001.27x Dapper1.08x Dapper
10,0001.74x Dapper1.04x Dapper

Forget gets worse as the id count grows. EF Core gets better. Both are consistent with the same cause: EF Core's single IN/= ANY query doesn't need batching at any scale, so its relative cost only reflects fixed overhead, which matters less as the row count grows. Forget's default batch does need more round trips as ids grow — 2 at 1,000, 20 at 10,000 — and each one costs something.

To confirm that story rather than just believe it, I added a variant that sets batchSize to the id count, so it always makes one round trip, the same as Dapper and EF Core:

connection.GetByIdRange<Product>(ids, batchSize: ids.Length);
idsOne round trip
1001.11x Dapper
1,0001.04x Dapper
10,0001.04x Dapper

Flat, and close to Dapper at every scale. Round trips were most of the story for reads — the rest is below. The batch exists for a real reason (those parameter limits are real, and a statement with thousands of parameters is its own cost), but on the one engine this benchmark runs against, a caller who wants a single round trip and knows their id count can ask for exactly that.

Writes bottleneck on something else entirely

InsertRange and UpdateRange looked like they should tell the same story: EF Core generates one statement per row, so I expected round trips to explain its cost here too, and expected it to get worse than Forget as the row count grew, the same shape as the read case.

The first surprise: EF Core doesn't actually make one round trip per row. Counting DbCommand executions with LogTo filtered to CommandExecuted showed it batches statements into chunks of exactly 1,000 per round trip — 1 round trip for 1,000 rows, 10 for 10,000. Not "one round trip," but not "one per row" either.

The second surprise is the one that mattered: at 10,000 rows, EF Core makes fewer round trips than Forget's own default batching (10 against 20, since Forget batches at 500). If round trips were the cost driver here, EF Core should be closing the gap, the same as it did on the read side. It doesn't:

rowsInsertRange, EF / ForgetUpdateRange, EF / Forget
1001.9x2.7x
1,0002.0x2.2x
10,0002.3x3.0x

EF Core gets worse relative to Forget as the row count grows, with fewer round trips the whole time. What actually scales badly is the number of separate SQL statements the database has to parse and plan: 10,000 single-row statements for EF Core against 20 multi-row statements (500 rows each) for Forget, at 10,000 rows. Round trips and statement count usually move together, which is why it's easy to credit the wrong one; here they didn't, and that's what made the real cause visible. Forget itself stayed close to a flat 13x–16x faster than the naive per-row Dapper baseline at every scale, batched or not — a number this second round of work never touched, because nothing in it needed to.

Making the client-side work disappear, for the operations that have any

A caller who already holds their ids as a typed array — int[] ids — was still going through a non-generic IEnumerable parameter, which means every id comes back boxed from the enumerator, gets its type checked individually, and gets copied into a runtime-typed array reflectively before it's bound as a query parameter. None of that is free, and none of it is necessary when the caller's type is already known at compile time.

So GetByIdRange and DeleteRange got a generic overload:

IReadOnlyList<Product> rows = connection.GetByIdRange<Product, int>(ids);

With TKey known, the type is checked once instead of once per id, the ids aren't boxed, and the array is built directly instead of through Array.CreateInstance/SetValue. The non-generic overload's own list of ids is also sized to the id count now, instead of grown one at a time — a smaller change, from the same family as the one the rest of this post is about, and the reason its own numbers below are lower than they were when this overload first shipped. Measured without a database, building the commands for 100, 1,000 and 10,000 ids takes

100 ids1,000 ids10,000 ids
GetByIdRange, non-generic2,401 ns (7.0 KB)20,694 ns (38.7 KB)210,245 ns (355 KB)
GetByIdRange, typed325 ns (3.8 KB)457 ns (7.3 KB)2,207 ns (42.5 KB)
DeleteRange, non-generic2,378 ns (5.8 KB)20,912 ns (37.4 KB)208,969 ns (354 KB)
DeleteRange, typed325 ns (2.5 KB)405 ns (6.1 KB)2,100 ns (41.2 KB)

7x to 100x faster, 44% to 88% less memory, and the gap widens with the id count, since the non-generic cost grows with it while the typed one barely moves. Against a real database, with round trips already equalized, the typed call landed at 1.04x Dapper at 10,000 ids against 1.07x for the non-generic one — a real but much smaller slice, because most of the total cost is still the query itself. That specific pair of numbers didn't stay still; the next section is about why.

GetById and Delete take a single identifier, not a sequence, and got the same typed overload for consistency. Here's the part I'd rather report than skip: it made no measurable difference. 204 ns against 194 ns, identical memory, both well inside the noise. A single id has no per-element loop for the typed path to skip — checking one id's type once is the same amount of work whether the compiler already knows the type or not. The win was in the loop, not in the concept, and a result that isn't there is still a result worth writing down.

The bug the benchmarks found, twice

Adding the typed GetByIdRange/DeleteRange overloads meant writing a test that both overloads build the same commands for the same ids. On SQL Server, with enough ids and an explicit large batchSize, that test failed — DeleteRangeCommands produced a command that, when actually executed, SQL Server rejected:

"The incoming request has too many parameters. The server supports a maximum of 2100 parameters."

My first read of that failure was that my new test was asking for more than a single command could hold, and that fixing the test — not the library — was the right call. It was pointed out to me that this deserved a second look before I moved on, so I went back to the code instead of trusting that first read.

GetByIdRangeCommands caps batchSize itself to the parameter limit before building anything. DeleteRangeCommands didn't: it capped the size of each chunk it builds at a time, and let batchSize — however large the caller passed — control how many chunks get combined into one command. Its own documentation already promised the parameter cap; the code just didn't do it:

// what it did
return DbCommandStrategy.Instance.DeleteRangeCommands(connection, entities, batchSize, SqlDialectStrategy.Instance.MaxParameterCount);

// what it does now
batchSize = batchSize > 0 ? Math.Min(batchSize, SqlDialectStrategy.Instance.MaxParameterCount) : SqlDialectStrategy.Instance.MaxParameterCount;
return DbCommandStrategy.Instance.DeleteRangeCommands(connection, entities, batchSize, 0);

DeleteRange/DeleteRangeAsync — the methods that actually execute — already capped batchSize correctly and were never affected. Only the method that just builds the commands for inspection or manual execution had the gap, and it had been there since before this round of work started.

Once that was confirmed, the obvious next question was whether InsertRangeCommands, UpdateRangeCommands and UpsertRangeCommands on SQL Server had the same shape of bug, since they build commands the same way. They did — same missing cap, same fix, same three tests written to build and actually execute the commands against a real database before trusting that the fix worked, because a command that merely looks reasonable and a command that actually runs are two different claims.

None of this showed up by reading the code and reasoning about it. It showed up because a test asked SQL Server to run something, and SQL Server said no.

What's in 2.3.0

Typed GetByIdRange, DeleteRange, GetById and Delete overloads on all four providers, and the parameter-limit fix above, on SQL Server's DeleteRangeCommands, InsertRangeCommands, UpdateRangeCommands and UpsertRangeCommands. The full numbers, the benchmark code, and how the suite is kept fair (same connection for every library, no change tracking for EF Core, every result checked against the Dapper baseline before it's trusted) are in the repository.

The typed overload still boxed on the way out

That shipped as 2.3.0. Re-running the same benchmarks against the release after it, the typed GetByIdRange had stopped boxing ids on the way in, but it still boxed them on the way out: a batched call deduplicates the rows it returns by id, which needs a set keyed by id, and that set was still a HashSet<object> — the same one the non-generic overload uses — because nobody had made it generic when the typed overload shipped. With round trips equalized, the typed call still measured a couple of percent behind EF Core's own query: small, but real across repeated runs, and the kind of gap this suite exists to chase rather than wave away.

The first guess was the dedup pass itself. A diagnostic variant — the same Dapper query, then the same HashSet-and-copy Forget does, with nothing else from Forget in between — cost about 0.1 to 0.3 ms per 10,000 rows, with the noise between runs wider than the cost. Real, but not the cost: on its own it didn't explain the gap.

The next step ran the exact command Forget builds, verbatim, through Dapper directly — no Forget code at all past the query. That landed at parity with the plain Dapper baseline. So the gap wasn't in the SQL or the parameters; it was somewhere in the few hundred lines of C# between the query returning and the typed overload returning. Rebuilding that work piece by piece, inside the same database benchmark, didn't settle it either — each piece moved by anywhere from 0.2 to 0.9 ms between otherwise identical runs, more than the effect being measured. The database round trip was too noisy an instrument for a question this small.

Moving the comparison out of the database, into a plain benchmark over 10,000 rows already sitting in memory, did settle it — measured both at rest and again after manufacturing about 2.7 MB of short-lived garbage first, to stand in for what a query leaves behind before the dedup pass runs:

Dedup passAt restAfter ~2.7 MB of garbage
HashSet<object> (boxed)202 µs~550–600 µs
HashSet<int> (typed)89 µs~120 µs

At rest, boxing 10,000 ids costs what boxing 10,000 integers should cost — real, but on its own still too small to explain a gap closer to a millisecond against a real database. Under a bit of memory pressure, the boxed version got about three times slower; the typed one barely moved. Measuring the garbage collector's own pause time directly (GC.GetTotalPauseDuration(), before and after each block) showed the pause itself accounted for almost all of that jump. A small harness that measured the same pause directly around the real database call confirmed it there too: the boxed dedup pass added about 290 µs of pause over the bare command; the typed one added none the harness could detect.

The fix was the one already applied to the input side in 2.3.0: make the dedup pass generic too. The typed overload now deduplicates with a HashSet<TKey> — a byte-content comparer when TKey is byte[], since .NET's own equality for a byte array is by reference — instead of boxing every id into the same set the non-generic overload uses.

The first measurement after that fix was a regression, not a win: allocation went up, from 3,403 KB to about 3,500 KB at 10,000 ids. The new set had no capacity hint, so it grew from empty to 10,000 entries through several internal reallocations, and that cost more than the boxed ids it had just stopped creating. The set can never hold more entries than ids given — a correct, exact upper bound, not a guess — so giving it that capacity up front, the same way the non-generic set already did, fixed it: 3,129 KB, below where it started before any of this, and the same number across three separate runs.

The same oversight — a collection grown one item at a time instead of sized to a count already in hand — turned up in a few other places once it was worth looking for: the boxed id list the non-generic overloads build (sized to the id count, since it's never discarded — the reason its own numbers in the section above are lower than when the typed overload first shipped), the list of commands the four providers build one batch at a time, and the list of values a Contains/In filter collects. The last two are correct upper bounds too, with no measurable effect at the sizes this suite benchmarks — a few dozen batches, 10 ids in the Contains case — fixed anyway, for the same reason, not for a number to report.

With one round trip, the typed call now measures at 1.05x, 1.02x and 1.03x Dapper at 100, 1,000 and 10,000 ids, against 1.29x, 1.13x and 1.03x for EF Core's own query. EF Core is the slowest of the three below 10,000 ids, where its per-call overhead is a bigger share of a shorter call, and roughly level with Forget at 10,000. The typed call also allocates less than EF Core at every count measured: 35 KB against 76 at 100 ids, 298 KB against 384 at 1,000, 3,129 KB against 3,573 at 10,000.

What's in 2.3.1

The typed GetByIdRange's dedup pass, no longer boxing ids; the boxed id list the non-generic GetByIdRange/DeleteRange overloads build, the list of commands the four providers build in batches, and the list of values a Contains/In filter collects, all now sized up front instead of grown one item at a time. No change in behaviour and no change to the public API; the numbers above, and the full suite in the benchmarks README, are the ones to quote now.
